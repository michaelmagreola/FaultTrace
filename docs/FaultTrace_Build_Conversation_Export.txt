# RouteIQ — Application Showcase

## Application Overview

**Name:** RouteIQ  
**Purpose:** Field service route optimization for HVAC, plumbing, and electrical teams.

RouteIQ gives dispatchers a fast way to assign jobs to the right technicians, cut unnecessary drive time, and keep customers in the loop — while technicians get a clear view of their day’s schedule.

**Problem it solves**  
Field-service shops often assign work by gut feel or sticky notes. That leads to mismatched skills, wasted windshield time, and customers who don’t know when anyone is coming. RouteIQ turns a day’s jobs into skill-aware, proximity-based assignments with drive-time metrics and simulated customer notifications — so dispatchers can optimize in one click and still override when needed.

**Target audience**
- Operations / dispatch managers at HVAC, plumbing, and electrical companies  
- Field technicians who need a simple daily job list  
- Students and reviewers evaluating a full-stack-style demo deployed on AWS

**Key features**
- **Role-based experiences** — Shared login for Dispatcher and Technician views  
- **One-click route optimization** — Greedy assignment by skill match, distance, and current load, with drive-time and efficiency stats  
- **Manual reassignment** — Override any job with skill-aware validation  
- **Customer notification log** — Simulated SMS confirmations after optimization  
- **Persistent, resilient demo session** — Restores jobs, assignments, and alerts after refresh, with validation, loading states, and error recovery

## Technical Report

### Architecture Overview

| Layer | Technology |
|-------|------------|
| **Frontend** | React 18, Create React App (`react-scripts`), Lucide React icons, CSS theme tokens |
| **Backend** | None (client-only SPA). Production static assets served with `serve` inside a Docker container |
| **Database** | None — state persisted in browser `localStorage` (`routeiq-app-state`) |
| **Routing logic** | Client-side greedy optimizer in `utils/routing.js` (skill + distance + load) |
| **Auth model** | Demo-account validation in the browser (not server auth) |

**AWS services used**
- **Amazon ECS Express Mode** — hosted gateway service for the containerized app  
- **Amazon ECR** — Docker image registry (`routeiq:latest`)  
- **IAM** — `ecsTaskExecutionRole` and Express infrastructure role  
- **Amazon CloudWatch Logs** — container logging for the ECS service  
- **GitHub Actions** — CI/CD deploy workflow to ECR + ECS Express (`deploy-ecs-express.yml`)

Container flow: multi-stage `Dockerfile` builds the CRA production bundle, then serves it on port `8080` via `serve -s build`.

### Development Journey

**Most challenging feature**  
Hardening a client-only demo into something that feels production-safe: trusted session restore (so `localStorage` can’t spoof a dashboard), allowlisted tech/skill IDs, sanitized persistence, CSP, and wrapping every critical action (login, optimize, reassign, logout) so failures never white-screen the UI — all without a real backend.

**Biggest learning moment**  
Taking a single-file prototype and shipping it as a structured React app on AWS: feature folders, validation/error UX, security controls, Docker packaging, and ECS Express + ECR + GitHub Actions. The leap wasn’t just “make optimize work” — it was making the demo durable, reviewable, and deployable.

### Known Issues

**Current bugs / limitations**
- Login is **demo-only** (client validation); not real authentication  
- SMS notifications are **simulated** (in-app log, no carrier/API send)  
- Job coordinates are a simplified grid — not real maps or road routing  
- No automated E2E suite yet (manual 47-item checklist; Playwright is available but not wired as CI smoke tests)  
- Full WCAG audit not completed (baseline a11y is in place)  
- CRA transitive `npm audit` noise accepted (not force-fixed)

**Features not yet implemented**
- Multi-user / multi-company accounts and real server auth  
- Live map view and turn-by-turn / road-distance routing  
- Real SMS (e.g. Twilio) and email notifications  
- Technician identity beyond the Carlos demo account  
- Admin job/tech CRUD and historical reporting  

**Scalability constraints**
- All state is per-browser `localStorage` — no shared multi-dispatcher source of truth  
- Greedy optimizer is fine for the demo seed set; not tuned for large fleets or hard time windows  
- ECS Express service sized for cost-aware demo traffic (small task size, limited scale range)  
- Static SPA hosting — no API tier to scale independently under load  

### Improvement Ideas

With more time, these three would be the highest-impact next features:

1. **Backend + real auth & data store** — Node/API Gateway + Cognito (or similar) and DynamoDB/RDS so dispatchers share live schedules securely  
2. **Map-based routing** — Mapbox/Google Distance Matrix (or AWS Location Service) for real drive times and a visual route board  
3. **Twilio (or SNS) customer SMS** — Replace the simulated log with real outbound confirmations and delivery status

## App under test

**ClaimGuide AI / ClearClaim Analytics** — role-based prototype for searching approved claims documentation with simulated RAG answers, citations, feedback, and an admin/usage panel. Deployed on **AWS Amplify** (Vite + React SPA).

**Advertised roles tested**

## What Works Well

1. **Citation-first RAG UX is excellent for claims work**  
   Asking *“What is the verified paid date requirement?”* returns **Answer found**, a **Medium confidence** meter, a plain-language answer, and a **quoted source** from *DMEPOS Documentation Guide § Verified Paid Date Checks*. Every answer also carries a human-review disclaimer. That combination is stronger than a generic chatbot for a compliance audience.

2. **Honest prototype framing + refusal behavior**  
   Login discloses simulated sign-in; the footer says simulated RAG. Out-of-scope questions (*“capital of Mars for DMEPOS”*, member claim-status style asks) correctly return **No sufficient source** instead of inventing policy. Role gating works: **Admin panel is hidden for Analyst**, visible for QA/Owner; **Continue** stays disabled until a role is selected.

3. **Admin panel tells a coherent ops story**  
   QA/Owner see approved-doc counts, helpful rate, document ingestion states (including a **Pending ingestion** draft), top questions chart, unresolved items, and feedback summary. Even as a prototype, it shows they thought beyond “chat box.”

---

## Improvement Suggestions

1. **Bug — duplicate “Continue to dashboard” CTAs**  
   - **Steps:** Open https://main.d1jvr2s7nwf3os.amplifyapp.com → do not select a role.  
   - **Result:** Two identical Continue buttons (one above roles, one below), both disabled. After selecting a role, both enable.  
   - **Why it matters:** Looks like a layout merge mistake; keyboard users get two equivalent stops.

2. **Bug / gap — feedback & queue loop doesn’t close**  
   - **Steps:** Sign in as Claims Analyst → ask a question → click **Needs QA review** or **Suggest correction** (textarea appears) → Sign out → sign in as QA Reviewer → open **Admin panel**.  
   - **Result:** Unresolved list/metrics look like **seed/demo data**; **Suggested Correction** stayed at **0** after submitting correction text; no Resolve/Clear actions on queue items.  
   - **Why it matters:** Login copy promises QA will “clear the review queue,” but the queue is mostly a static dashboard.

3. **UX / feature gap — Owner “manage documents” is view-only**  
   - **Steps:** Sign in as Documentation Owner → Admin panel.  
   - **Result:** Ingestion status is visible (Active / Pending), but there is no Upload / Approve pending / Deactivate control.  
   - **Suggestion:** Add “Approve pending ingestion” for *DMEPOS Guidance Update — Q3 draft* and a simple upload path.  
   - **Use case:** Owner publishes a Q3 guidance update; Analysts immediately search the new approved set; QA verifies citations against the new version.

**Also noted:** browser tab title is still **“ClaimGuide AI Local Prototype”** on Amplify; Ask box relies on placeholder only (no accessible name); reload returns to login (no session persistence).

## One Priority Fix

**Make the human-in-the-loop path real: Analyst feedback must create/update QA queue items, and QA needs Resolve/Clear actions that change the metrics.**

Why: citations + confidence are already impressive, but the product story is “search → flag → review → improve docs.” Right now the middle of that story is cosmetic. Closing that loop would turn a strong demo UI into a believable workflow.

## Claude Code vs classmate’s coding tool

The live ClaimGuide build **does not credit** which AI coding assistant was used. From the artifact shape (**Vite + React SPA**, Tailwind-style utilities, **Amplify** hosting), the workflow matches a typical **AI IDE / pair-programmer** build (commonly **Cursor** in this kind of course track). Below is a direct comparison of **Claude Code** vs that **AI IDE (Cursor-style) workflow**.

| | **Claude Code** | **Classmate’s likely tool (AI IDE / Cursor-style)** |
|--|-----------------|------------------------------------------------------|
| **Workflow** | Terminal-first agent: describe a goal, it plans, edits files, runs commands, and iterates in a repo session. Strong for “stay in the project and ship.” | Editor-first: chat + inline edits + composer beside the code; preview/deploy often wired through the IDE; great for UI iteration and Amplify/Vite apps. |
| **Strengths** | Deep multi-step repo tasks, shell/test loops, large refactors, fewer context switches once the agent is running. | Fast visual product loops (login card → role dashboards → admin widgets), easy screenshots/preview, low friction for frontend polish and hosting. |
| **Risks** | Can over-edit or run broad command sequences if prompts are vague; weaker “see the pixel” loop unless you add browser tooling; easier to accumulate backend complexity you didn’t need. | Can produce a beautiful SPA that **looks** complete while workflows stay mocked (exactly what we see: simulated RAG, static admin queue). Also easy to leave “Local Prototype” titles/duplicate CTAs when generating UI quickly. |

**Bottom line for this peer app:** ClaimGuide’s strengths (clear domain UX, citations, role split, Amplify deploy) look like an AI-IDE-accelerated frontend win. Its gaps (non-mutating QA queue, view-only Owner admin) are the classic risk of that workflow—**shipping the screen before the state machine**. Claude Code’s risk profile is the inverse: it may push harder on wiring/persistence/tests, but can under-invest in the polished claims-console UX this teammate clearly prioritized.

Application description

FaultTrace is a full-stack retrieval application. A technician types a fault code or describes a symptom. Then the app now fulfill the requirements below:                                                                         Part 1: New AI Use Case (Manufacturing)

App: FaultTrace, a maintenance knowledge system for plant floor technicians

Company context and current challenges

Cardinal Precision is a 200-person contract manufacturer running CNC machining and assembly across two shifts. Maintenance history lives in a CMMS export of roughly twenty years of work orders, plus paper binders in the shop office. Three of the five senior technicians retire within four years, and their knowledge is not written down. When a machine faults at 2 a.m., the technician on shift either remembers the fix or starts from zero.

The business problem

Repeat faults get diagnosed from scratch. The history that would shorten the repair exists, but nobody can find it. Work orders were typed by different people over two decades, so one failure appears as spindle drift, spndl drift, SPIN-DRFT, and axis wander. Keyword search returns nothing or everything. On a bottleneck cell, an hour of unplanned downtime stops the line, not just the machine.

Target users and their needs

Technicians on shift need an answer in under two minutes, on a tablet, standing at the machine wearing gloves
The maintenance planner needs to see which faults keep recurring and which parts to stock
The plant manager needs downtime by asset and cause, in numbers, for the weekly production meeting
Why AI is the right solution

The blocker is unstructured text with inconsistent vocabulary, which is where keyword search fails and semantic retrieval works. Embedding search finds prior work orders describing the same failure in different words. A language model then summarizes what actually fixed it. Every answer cites the work order numbers behind it, and the app says it found nothing rather than inventing a procedure. Safety documents are linked, never generated. The technician decides. The model retrieves and drafts.

Success metrics

Median time from fault logged to first corrective action, against existing work order timestamps
Mean time to repair on repeat faults compared with first occurrences
Share of closed work orders where the technician marked a suggested prior case as useful
Retrieval accuracy on 30 held-out fault and fix pairs, scored as correct work order in the top five
MVP features

Symptom or fault code search returning ranked prior work orders
Grounded summary of what fixed it before, with linked work order IDs
Structured close-out form capturing cause, fix, parts used, and minutes down
Per-asset history page
Supervisor view ranking recurring faults by total downtime minutes
Part 2: Technical Plan (FaultTrace)

Application description

FaultTrace is a full-stack retrieval application. A technician types a fault code or describes a symptom. The backend embeds that query, runs a vector search against twenty years of work orders, and passes the top matches to a language model with instructions to summarize the fix and cite the work order IDs it used. If nothing relevant comes back, the app says so instead of generating a procedure. Every close-out writes a new structured record, so the corpus improves with use.

Technology stack and justification

Frontend: React 18 with Vite and TypeScript. Tablet-first layout, large touch targets, and high contrast, because the user is standing at a machine wearing gloves. TypeScript because a shared API contract is worth the setup cost once a real backend exists.
Backend: FastAPI on Python. The embedding, retrieval, and prompt orchestration all live server side, and Python has the shortest path to that work. A real REST API this time, not browser-only logic.
Database: PostgreSQL on Amazon RDS with the pgvector extension. Work orders, assets, parts, and embeddings sit in one database, which avoids running a separate vector store for a corpus this size.
Auth: Amazon Cognito with technician, planner, and admin roles. Server-enforced, not a client-side check.
AI: Claude through Amazon Bedrock for generation, with an embedding model for retrieval. Retrieval-grounded, with citations required and a refusal path when confidence is low.
Ingestion: a one-time normalization and embedding job for the CMMS export, then incremental embedding on each close-out.
Key features and how they solve the problem

Semantic search solves the vocabulary problem directly, since spndl drift and axis wander land in the same neighborhood. The cited summary turns ten prior work orders into one answer a technician can act on in under two minutes. The structured close-out form fixes the root cause of the mess, which is that free-text notes were never captured consistently. The supervisor view converts the same data into downtime by asset and cause, which is what the weekly production meeting actually needs.

ASSISTANT (292)

**FaultTrace** is a maintenance knowledge app for plant-floor technicians at Cardinal Precision, a contract CNC/assembly manufacturer.

**The problem:** Years of work orders sit in a CMMS (and paper binders), but when a machine fails at 2 a.m., that history is hard to find. The same fault was written many ways — *spindle drift*, *spndl drift*, *SPIN-DRFT*, *axis wander* — so keyword search returns nothing or noise. Senior techs who “just know” the fix are retiring. On a bottleneck cell, that wasted hour stops the line.

**The use case:** A technician types a symptom or fault code on a tablet at the machine. FaultTrace finds similar past work orders with semantic search, summarizes what fixed it before, and cites the work-order IDs. If nothing reliable matches, it says so instead of inventing a procedure. Close-outs are structured so the knowledge base improves. Supervisors see recurring faults and downtime for the weekly meeting.

**In one line:** FaultTrace turns buried, messy maintenance history into a cited answer in under two minutes — so the floor doesn’t start from zero every time.
